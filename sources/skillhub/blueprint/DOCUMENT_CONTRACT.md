# 文档记录模板与交付合同

按当前阶段实例化，示例ID是格式说明，不是已发生的事实。每份规划文档独立 `.md`，存在既有 canonical 文件时登记映射并更新原件。以下模板是文档约定，不是可执行验证器。

## 文档头与阶段台账

```text
文档ID / canonical路径 / 当前版本 / 状态
原始目标 / 最新修正 / 范围 / 不做
上游文档ID及版本 / 来源及读取日期 / 实际作者
假设HYP / 建议SUG / 待决策DEC / 风险RISK
确认者 / 用户确认原话 / 确认日期 / 确认版本
```

`docs/00-planning-state.md`：

| 阶段0–6 | 文档路径与版本 | 状态 | 上游版本 | DoD证据 | 审查人及类型 | 用户确认原话/日期/版本 | 阻塞 | 下一验收点 |
|---|---|---|---|---|---|---|---|---|

同一Agent多角色时类型写 `SELF_CHECK`；实际独立审查写 `INDEPENDENT_REVIEW`，附真实执行者与记录。没有审查写 `NOT_REVIEWED`，不填假姓名。

`docs/requirements-traceability.md`：

| REQ-ID | 证据/HYP | JTBD | Epic/US-ID | 优先级/版本 | 功能ID | 页面/业务状态 | 设计规范 | 实体/接口/ADR | TASK-ID | AC/TEST-ID及预期 | 实际证据/未验证 | 排除理由 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

阶段2初始化，阶段3补功能/页面，阶段4补架构，阶段5补任务，阶段6双向审计。每阶段的未来列允许写“待阶段n”，最终P0不能保留关键待补。尚未写测试时 `TEST-ID` 只是计划，不能标执行成功。范围外/延期条目注明确认决定和归属版本。

## 阶段 2 Mermaid 架构草图（详细契约前置）

`docs/02-architecture-sketch.md` 是新项目在详细 PRD/API/数据/Agent 契约前的初步架构基线：目标/最小闭环、系统边界、Mermaid `flowchart`、数据流及失败恢复、取舍、风险/假设、来源与未决项。复杂业务交互可补 `sequenceDiagram`，关键状态补 `stateDiagram-v2`，实体关系补 `erDiagram`；简单项目不凭空生成不适用图。

经真实 SA/CTAB/QA 视角自检或独立复核后按阶段2现有确认规则固定图的 SHA/版本。阶段3详细合同引用此版本；阶段4正式架构记录差异与取舍；架构边界发生变化按原 CHG 使阶段2及后续审查失效。已有项目沿用既有已确认架构或明确获准的迁移映射，不在旧文件上静默增加强制门禁。

结构检查只能证明 Mermaid fenced block 与必要讨论存在，不证明浏览器渲染、运行性能、安全性或真实独立审批。

## 交叉审查与DoD

每阶段适用审查行：

| 阶段/版本 | 视角及责任 | 实际执行者 | 自检/独立/未审查 | 审查输入及版本 | 发现/严重度 | 修正与复查证据 | 结论/阻塞 |
|---|---|---|---|---|---|---|---|

- 0–1：PM/CPO看用户价值与证据；研究/反方检查替代方案与可证伪性。
- 2–3：UX/UI检查任务/页面与设计依据；SA检查对象状态；QA检查验收可观察性。
- 4：CTAB/SA检查基线、成本、边界；设计和QA检查产品约束是否保留。
- 5–6：工程检查输入、依赖与可执行性；QA检查追踪、异常、适用测试和证据；CPO/PM检查范围与价值。

审查意见不一致时记录裁决和理由。没有实际执行者时保留缺口；不要让用户误以为多角色发言等于独立验收。调用集团协调器时使用现有 `scripts/board-workflow.py`，不在此另实现状态引擎。

`docs/05-definition-of-done.md`：

| 交付层级 | 适用项 | 条件 | 所需证据 | 实际状态 | 审查责任 | 不适用理由 |
|---|---|---|---|---|---|---|
| 规划 | 文档/确认/一致性 | 追踪完整、阻塞消除、版本确认 | 文档与确认/审计记录 | 待验证 | PM/CPO及适用审查人 | |
| 原型 | 另行授权后 | 核心流程及状态、设计合同 | 实际页面、点击与截图 | 未执行 | UX/UI及独立审查 | |
| 工程 | 另行授权后 | 输入→处理→输出、恢复与适用检查 | 对应版本运行与测试 | 未执行 | 工程及独立QA | |
| 发布 | 另行授权后 | 环境、回滚、部署后读回 | 发布与正式环境证据 | 未执行 | OPS及独立QA | |

## 任务、变更和交接

Kanban行至少：`TASK-ID / REQ-US-AC / 输入版本 / 输出 / 依赖 / 负责人 / 估时依据 / 状态 / 检查与审查证据 / 阻塞 / 失败回流`。TODO只列 `TASK-ID / 下一动作` 并链接看板，不独立维护Done。

变更行至少：`CHG-ID / 原版本与决定 / 原因 / 新方案 / 影响ID和文档 / 成本风险 / 迁移回退 / 批准原话和日期 / 失效确认 / 重新审查版本`。

AGENTS/CLAUDE草案分别保存为 `docs/05-AGENTS-draft.md` 和 `docs/05-CLAUDE-draft.md`；CLAUDE引用共享规范，注明优先级和工具差异。根文件已存在时先审阅并出最小diff；独立授权应用后记录根文件路径和版本，不整份替换。

交接列：当前目标、阶段批准、文档索引及版本、稳定范围、不做、设计/技术决定、追踪矩阵、首个READY任务、DoD、风险和证据缺口、未执行项、原型/开发/付费/部署分别是否授权。只规划时一律不宣称实现、独立QA、上线、订单或盈利。
