# 项目控制面最小集（可复用模板）

把「状态、边界、判定」从参与者记忆里剥离出来，固化成机器可读、可判定的文件。
适用于**多会话、多参与者、长周期**的项目。一次性脚本不需要这个。

配套方法论见 `docs/EVIDENCE_LAYERING.md`。

---

## 一、三份文件

### 1. `AGENTS.md` — 给 Agent 的唯一入口

读这一份就能开工，不需要再问人。建议结构：

```markdown
# AGENTS.md — <项目名>

> 给 Agent 的唯一入口。用户向文档是 README.md，技术细节是 docs/ARCHITECTURE.md。
> 最后更新：<日期>

## 这是什么
<一句话>

## 30 秒上手
<能直接粘的命令：怎么跑、怎么验、怎么打包>

## 铁律（违反会出事）
| # | 铁律 | 原因 |
|---|---|---|
| 1 | <不能动的东西> | <为什么> |
| 2 | <不能破坏的路径> | <为什么> |
| 3 | 新增能力只能是加法 | 已有链路一条都不能删 |
| 4 | 改了就要回扫文档 | 别只改一处 |
| 5 | 不许说「完成」而不给证据 | 见下 |

## 测试分层（几层，各证明什么）
| 层 | 测什么 | 文件 | 漏了会怎样 |

## 完成判定（外部判定，不许自证）
| 声称 | 必须附的证据 |

## 关键事实（省得重新踩）
<那些"看起来是 A 其实是 B"的坑，一条一句>

## 目录导航
## 常见任务怎么下手
## 当前状态
```

**关键点**：「铁律」和「关键事实」是这份文件的价值所在。
普通文档写「项目是什么」，`AGENTS.md` 写「什么事绝对不能做，为什么」。

### 2. `TASKS.md` — 任务状态机（不是待办列表）

```
PROPOSED → READY → CLAIMED → IMPLEMENTING → VERIFYING → [AWAITING_HUMAN] → DONE
任意状态 → BLOCKED            验证失败 → 回 IMPLEMENTING
```

| 状态 | 准入条件 |
|---|---|
| `READY` | 必须写清「怎么算完成」 |
| `CLAIMED` | 写明谁认领、认领时间 |
| `VERIFYING` | 必须有可执行的验证命令 |
| `AWAITING_HUMAN` | 必须写清「要人决定什么」 |
| `DONE` | **必须有证据**（命令输出/产物校验/截图） |
| `BLOCKED` | 必须写清阻塞原因**和解除条件** |

**铁律：不许从 `IMPLEMENTING` 直接跳 `DONE`。**

待办列表的致命缺陷是**它不记录「为什么没做完」**。
三天后回来看 `[ ] 修某个东西`，完全不知道当时卡在哪、试过什么。
`BLOCKED` 强制写阻塞链，下次不用重新试错。

### 3. `scripts/check.sh` — 分层门禁

```
第一层 静态：语法 / 清单 / 打包 / 界面断言
第二层 真机：界面布局 → 集成层 → 能力层 → 产物层
```

设计要点：

- 每层输出 `PASS / FAIL / SKIP` **加一句人话**说明这层证明了什么
- `SKIP` 要带原因（「加 --full 启用」/「宿主不可用」/「被限流，不算失败」）
- 区分「产品坏了」和「外部因素导致没测成」——后者不该报 `FAIL`，否则会让人对门禁麻木
- 支持 `--static`（快）/ `--full`（慢）/ `--json`（机器读）
- 退出码：0 全绿 / 1 有失败 / 2 全部跳过

## 二、事故记录（写进 TASKS.md 顶部）

```markdown
## 事故记录

### A-001 · <一句话>
- **现象**：用户看到什么
- **根因**：机制层面的原因（不写「疏忽」）
- **违反的原则**：违反了哪条判据
- **修复**：分条列出
- **额外发现**：顺带暴露的其他事实
```

编号永久保留，不删不改写。

---

## 三、装配顺序（不可颠倒）

1. **先写 `AGENTS.md`**：逼自己把「不可做的事」和「已知的坑」说清楚
2. **再写 `TASKS.md`**：把当前手上正在做的事按状态机记一遍
3. **最后写 `check.sh`**：把「怎么算完成」变成命令

反过来做（先写门禁）会失败：你会写出「能跑但不知道该断言什么」的脚本。

---

## 四、反模式

| 反模式 | 为什么错 |
|---|---|
| 用待办列表代替状态机 | 不记录阻塞原因，下次重踩 |
| 门禁只报 PASS/FAIL 不解释 | 没人知道这层到底证明了什么 |
| 把外部限流当失败 | 门禁变噪音，人开始无视告警 |
| 允许 Agent 自评完成 | 「测试过了」的门槛会一路下滑 |
| 文档写得比证据完善 | 后来者按文档操作必然撞墙 |
| 一个 `check.sh` 里混所有层 | 慢层拖累快层，最后没人跑 |

## 五、自检清单

- [ ] 新会话的 Agent 只读 `AGENTS.md` 就能接着干，不用问人
- [ ] 每条「完成」都绑定了可复现的命令和可核对的输出
- [ ] `BLOCKED` 的项都写了阻塞原因和解除条件
- [ ] 门禁每层输出都有一句「这层证明了什么」
- [ ] 界面每个视图都被检查过（不是只看默认状态）
- [ ] 出过的事故都有编号记录
