# 交互证据：为什么「读状态」不等于「点得动」

2026年11月3日 · 从一次真实的 UI 走查事故里提炼。

## 一、事故形状

产品里有个设置齿轮。点击处理是：

```js
$('settingsBtn').addEventListener('click', () => {
  try { chrome.runtime.openOptionsPage(); } catch (e) { /* ignore */ }
});
```

而 `manifest.json` 里 `options_page` 指向的页面**功能极度单薄**（只有一个输入框），
更关键的是：**这一行在任何静态检查里都不会失败**。

自动化跑出来全绿：

- 按钮存在 ✅
- 按钮尺寸 44×44 ✅
- 点击区域够大 ✅
- 事件监听器已绑定 ✅

**但真人点下去，什么都没发生。**

## 二、根因：把「读状态」当成了「操作」

常见的一类伪验证：

```js
await page.evaluate(() => document.getElementById('btn').click());   // 看起来像点击
```

它绕过了真实交互里最容易出问题的那几层：

| 被绕过的 | 真实用户会遇到 |
|---|---|
| 命中测试（有没有元素盖在上面） | 浮层遮挡点不到 |
| 可见性（是否在视口内 / 被裁掉） | 按钮滚出可视区 |
| 指针事件链（pointerdown/mousedown/click） | 只绑了 mousedown 的代码不触发 |
| `disabled` / `pointer-events: none` | 看着能点，其实点不动 |

**所以「点得动」这件事，只能用真实输入验证。**

## 三、做法

### 3.1 用坐标真点

```js
const box = await page.evaluate((id) => {
  const el = document.getElementById(id);
  const r = el.getBoundingClientRect();
  return { x: r.x + r.width / 2, y: r.y + r.height / 2, w: r.width, h: r.height };
}, id);
if (!box || box.w <= 0 || box.h <= 0) return fail(id, '元素不可见');
await page.mouse.click(box.x, box.y);     // 走真实命中测试
```

### 3.2 断言「点击有后果」，而不是「点击没报错」

点击成功的判据必须是**状态发生了预期变化**：

- 视图切换了
- tab 数量变了
- 某个元素的值改了
- 出现了新的 DOM 节点

**「没抛异常」不构成成功**——上面那个齿轮的例子就是既没抛异常也没反应。

### 3.3 完整性断言：该有的必须都在

尺寸检查只能证明「现有的按钮是好的」，证明不了「该有的按钮没丢」。

所以要另立一张清单：

```js
const REQUIRED = {
  ready:    ["download"],
  progress: ["cancel"],
  catch:    ["catchArm", "catchArmAv", "catchRefresh"],
  history:  ["histRefresh", "histClear"],
  settings: ["setSubDir", "setSave", "setBack"],
};
// 缺任何一个就报错，而不是「没找到就跳过」
```

**「找不到就跳过」是检查类代码最大的陷阱**——它会把「功能整个消失」变成「一切正常」。

### 3.4 主按钮也要真点，但要有受控副作用

「下载」「保存」这类主按钮点了会真的产生副作用，所以要配合：

- 本地 fixture（`chrome-extension://` 同源资源，不依赖外网）
- 临时下载目录 + 跑完清理
- 断言产物（解析器读出来 codec/时长），而不只是「没报错」

## 四、检查清单（接入新项目时）

- [ ] 每个视图的「必需元素」有没有硬编码成清单？缺了会不会报错而不是跳过？
- [ ] 走查是不是用真实坐标点击，而不是 `el.click()` 或直接调函数？
- [ ] 每次点击后断言的是「状态变化」，不是「没有异常」？
- [ ] 主按钮有没有在受控副作用下真点过一次？
- [ ] 有没有一个视图，因为「默认不显示」而从来没被检查过？

## 五、延伸：这条原则不只适用于 UI

同一类错误在其他层面的样子：

| 层面 | 伪验证 | 真实验证 |
|---|---|---|
| UI | `el.click()` | 鼠标坐标点击 + 状态变化断言 |
| 网络 | 直接调业务函数 | 发真实请求走完整链路（DNS/TLS/代理） |
| 安装 | 读配置文件说有 | 真的启动一次并探活 |
| 构建 | 断言产物文件存在 | 用产物真的跑一次 |

**共同的判据**：**验证要尽量靠近用户实际走的那条路。**
离得越远，假阳性的概率越高。

## 六、一句话

> **「没报错」是最弱的证据。**
> 判断一件事成没成，要看它留下的痕迹对不对，而不是看它有没有喊疼。
