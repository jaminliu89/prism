# AX 树 vs 视觉：为什么两者缺一不可

2026年11月3日 · macOS 实测。

## 一、常见但错误的说法

> 「放弃截图，拥抱无障碍树。AX 树 100% 精准，不用截图，毫秒级。」

前半句对（AX 确实比截图快、比猜像素准），**后半句错**：

**AX 树里有节点 ≠ 屏幕上有东西。**

## 二、实测反例

某 Electron 桌面客户端的更新提示浮层：

```
AXStaticText  发现新版本：v1.39.11   pos=(501,224)  size=118x14
AXButton      更新说明              pos=(964,216)  size=70x30
AXButton      下载、安装并重启        pos=(1044,216) size=116x30
AXButton      稍后                  pos=(1170,216) size=46x30
```

**位置、尺寸、角色、名字全都有**——看起来完全可点。

但按 (1102, 231) 裁图出来是：

```
"…结论以源码为准，不是猜的。"
"joeseesun/qiaomu-clipper，2026-10-02 建仓"
"证据 / package.json / webpack.config.js"
```

**一段对话文字，根本没有按钮。**

原因：应用把**已关闭浮层的 AX 节点留在了树里**。Electron 应用尤其常见。

**只信 AX 就会点在别的东西上**——而且不报错。

## 三、正确的做法：AX 定位 + 视觉复核

```
1. AX 树按语义找元素（快、准、有角色）
2. 拿到 bounds
3. 裁出那块区域，算像素方差
4. 方差过低 = 视觉上是空的 → 不点，并告诉调用方为什么
5. 方差正常 = 可以点
```

视觉复核用**像素方差**而不是截图体积：

| 判据 | 问题 |
|---|---|
| 截图体积 | 会被 PNG 压缩率、色彩复杂度干扰；纯色大图也可能很大 |
| **像素方差** | 缩到 8×8 灰度算标准差，纯背景接近 0，有内容明显更高 |

实测判别力（阈值 8.0）：

| 区域 | stddev | 判定 |
|---|---|---|
| 菜单栏（有文字） | 30.4 | 有内容 ✓ |
| 菜单栏（有图标） | 19.4 | 有内容 ✓ |
| 屏幕中部（有内容） | 8.9 | 有内容 ✓ |
| 4×4 极窄条 | 2.2 | 空白 ✓ |

## 四、顺带修掉的两个静默坑

### 4.1 AppleScript 数字拼接必须 `as string`

```applescript
-- ❌ 静默失败，整个脚本返回空
set out to out & role & "\t" & px & "\n"

-- ✅
set out to out & role & "\t" & (px as string) & "\n"
```

少了它，`_ax_elements` 返回空列表，表现成「这个应用没有可点的元素」——
而它其实有 800 多个。

### 4.2 `screencapture -R` 必须放在文件名之前

```bash
screencapture -x -o file.png -R 0,0,300,24    # ❌ 截全屏 3456x2234
screencapture -x -o -R 0,0,300,24 file.png    # ✅ 300x24
```

放错位置**不报错、返回码 0**，但截的是全屏。
后果：视觉验证永远拿到全屏方差，所有区域得到同一个数——
看起来像「判别力不行」，实际是根本没截对区域。

## 五、什么情况下该用哪个

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 找有语义的控件（按钮/输入框/菜单） | **AX 树** | 有角色和名字，可断言 |
| 验证「那个位置真的有东西」 | **视觉复核** | AX 会留幽灵节点 |
| 找 AX 拿不到的内容（画布、渲染文本、图片里的字） | **OCR** | AX 里根本没有 |
| 判断「操作生效了没有」 | **前后快照对比** | 双信号：画面指纹 + 结构摘要 |
| 知道坐标但要判断能不能点 | **像素方差** | 便宜、不需要模型 |
