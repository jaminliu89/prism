# 证据分层：为什么「测试全绿」不等于「产品可用」

2026年11月3日 · 从一次真实交付事故里提炼的判据。

## 这份文档解决什么

> 「你的单测、回归测试就是让我无法下载啊。」

上面这句话是真实用户反馈。当时的处境是：
**七八层测试全绿、CI 全过、门禁无告警，但用户点一下面板就报错。**

根因不是某一行代码写错，是**测试证明的东西和用户实际做的事不是一回事**。
这份文档把「证据要分层」这件事固化成可检查的结构，避免同类误判。

## 一、核心判据

**命令返回 0、HTTP 返回 200、JSON 里有 `"ok": true`，都不构成「功能可用」的证据。**

它们只证明「这一段代码跑完了」。产品可用需要证明的是另一件事：
**用户从他实际会点的那个入口进去，走到他要的结果，中途每一层都成立。**

## 二、五层模型

一次完整的交付验收至少分五层，每层证明不同的东西。**缺任何一层，都会有整类 bug 漏过去。**

| 层 | 证明什么 | 不证明什么 | 典型手段 |
|---|---|---|---|
| **1 静态** | 语法、清单、打包、引用完整 | 功能能不能用 | 语法检查、manifest 校验、打包产物清单 |
| **2 界面布局** | 控件存在、可见、够大、不溢出 | 点了有反应 | 逐个视图量真实渲染尺寸（见第四节） |
| **3 集成层** | 模块之间的消息链路通 | 端到端能出结果 | 在真实宿主里发真实消息，断言返回结构 |
| **4 能力层** | 某个技术手段本身成立 | 产品路径也成立 | 直接调该能力的原始接口 |
| **5 产物层** | 最终产物能打开、内容正确 | 用户操作路径顺畅 | 用解析器读产物并断言关键字段 |

### 最常被漏掉的是第 3 层

真实事故的形状是这样的：

```
能力层测试：直接用自动化工具在目标页面注入 hook，拿到 590 个分片      ✅
用户实际路径：点面板 → 消息 → 后台 → 解析器 → 本地服务 → 下载         ❌
```

**中间隔着一整层宿主代码**（消息路由、模块加载、参数传递、错误回传）。
那一层里的问题，能力层测试**一个都测不出来**：

- 某条通道仍在调用已被环境禁用的旧机制（菜单/ID/权限全对，仍被编译层拒绝）
- 参数对象里的字段名写错（如把模式放在 `d.mode` 而实际在 `d.payload.mode`）
- **测试自己的断言字段名也写错**（检查 `res.video.url`，实际数据在 `res.muxed[]`）

最后一条尤其危险：**断言写错会让你得到"测试通过"的错误结论**，
而不是"测试失败"。**测试本身也需要被审视。**

## 三、每层都要能回答「它证明了什么」

门禁输出不能只给 PASS/FAIL，要能读出**这一层证明了什么、没证明什么**。
建议每层输出一句人话：

```
PASS  静态层（语法/清单/打包/界面断言） — 32 项断言
PASS  界面布局（9 个视图逐一量尺寸） — 18 个按钮，最小高 28 px
PASS  集成层（真实宿主发真实消息） — 7 项判定全通过
PASS  能力层回归 — 86 个分片 / 1,945,119 字节
PASS  产物层（解析器验） — 10 项判定 | (3336959, 145.9, 'hevc,aac')
```

这样当有人问「你怎么知道它真的能用」，答案是一排能复现的命令和它们的真实输出，
而不是一句「测试过了」。

## 四、界面层的两个具体做法

### 4.1 逐个视图量尺寸，不看默认状态

有 N 个视图的界面，**默认通常只显示 1 个**。只截默认状态，等于 N-1 个视图从没被检查过。

做法：遍历所有视图，逐个切成可见，然后对每个可见元素量 `getBoundingClientRect()`：

- 高度 ≤ 0 → 布局坏了
- 按钮高度 < 26px → 可点击区域太小（触控板 / 触屏上很难点中）
- `right > 容器.right + 1` → 横向溢出
- 按钮文案为空 → 用户不知道这个按钮干什么

**实战收益**：一次就抓出 9 个按钮只有 19px 高（样式里 `padding: 2px 0` 导致的），
以及两个主按钮上下紧贴、视觉上糊成一块。

### 4.2 空白检测：一个视图里连一句话都没有

只查「带 id 的元素」会漏掉纯视觉内容（骨架屏、占位块）。
补一条更朴素的判据：

```js
// 统计该视图里所有可见的直接文本节点，低于阈值就是白板
const visibleText = [...root.querySelectorAll("*")]
  .filter(el => {
    const cs = getComputedStyle(el);
    if (cs.display === "none" || cs.visibility === "hidden") return false;
    return [...el.childNodes].some(n => n.nodeType === 3 && n.textContent.trim());
  })
  .map(el => el.textContent.trim()).join(" ");
if (visibleText.length < 4) problems.push("view 里几乎没有文字——用户会看到白板");
```

**实战收益**：抓到一个列表视图在空数据时**一片纯白**——
空态文案只写在渲染函数里，HTML 里是空的；渲染没跑到时用户就面对白板。
另一处是骨架屏只有几个灰块、没有一个字的说明，用户分不清是「正在读取」「卡住了」还是「坏了」。

**修法不是加渲染调用，是给 HTML 兜底文案**：渲染跑到时覆盖它，没跑到时至少不空白。

## 五、不许自证

**同一个执行者不能给自己的产物签验收。**

- 「我改完了」→ 不算完成
- 「测试过了」→ 要给出命令和真实输出
- 「应该没问题」→ 没有这个状态

每条「完成」必须绑定**可复现的命令**和**可核对的输出**：

| 声称 | 必须附的证据 |
|---|---|
| 下载能用了 | 解析器读产物，给出 codec / 分辨率 / 时长 |
| 界面改好了 | 布局断言通过，且逐视图截图可核对 |
| 宿主加载了新代码 | 读宿主的版本注册信息，不是看文件修改时间 |
| 这条链路通了 | 一次真实目标站点的成功记录，含耗时与字节数 |

## 六、事故记录格式

发现整类问题后，除了修，还要**留下能阻止复发的记录**。最小字段：

```markdown
### A-00N · <一句话说清事故>
- **现象**：用户看到什么
- **根因**：为什么（不要写"疏忽"，要写机制）
- **违反的原则**：违反了哪条判据
- **修复**：改了什么（分条）
- **额外的发现**：这次顺带暴露的其他事实
```

事故编号永久保留，**不删也不改写**——它的价值在于「后来者能查到当初为什么这么改」。

## 七、这套结构落地要多少成本

以一个中等规模前端扩展为例：

| 层 | 实现成本 | 运行耗时 |
|---|---|---|
| 静态 | 已有 CI 直接用 | 秒级 |
| 界面布局 | 一个脚本，约 150 行 | 2-3 秒 |
| 集成层 | 一个脚本，约 130 行 | 10-20 秒 |
| 能力层 | 一个脚本，约 120 行 | 20-40 秒 |
| 产物层 | 复用集成层 + 一个解析器调用 | 秒级 |

**总计约 400 行测试代码**。相比「用户点不动 → 排查 → 改 → 再点不动」的往返，
这个成本一轮就赚回来了。

## 八、一句话

> **测试全绿只证明你测过的东西是绿的。**
> 先问「我测的这一层，和用户走的那条路，中间隔了什么」，再决定测试写在哪。
