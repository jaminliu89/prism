# 交付与分发工程（macOS 桌面端）

2026年10月31日。来源：一次真实发版（[jaminliu89/video-to-text](https://github.com/jaminliu89/video-to-text) v0.5.2，固定提交 `b8261f45d90cc5ec9353769ac78d575b4b264dc3`）。文中的每条陷阱都有实际发生记录，见 [证据记录](verification/release-engineering/README.md)。

## 这是什么

把「我这台机器上能跑」变成「用户双击能装」的判据集：PyInstaller 打 `.app`、静态依赖注入、签名、`hdiutil` 封 DMG、GitHub Actions 发版，以及这条链路上会反复复发的那几个坑。

## 这不是什么

- **不是发布授权**。走查/上线仍由既有 delivery-walkthrough 与 checklist 主责，本文件只给判据和证据要求。
- **不是新的构建平台**。打包脚本留在各产品主库，Prism 只维护判断、合同与验收，不复制实现。
- **不认证安全**。ad-hoc 签名不等于公证，用户首次打开仍要右键→打开；这条必须写进用户可见的说明里。
- **不证明产品可用**。本文件全部通过，只说明「分发链路没有已知缺陷」，不说明产品功能正确。

## 五条原则

1. **可运行才算通过。** 检查 `Info.plist` 存在、`.app` 目录结构正确，都不代表它能启动。必须真的启动一次并访问它该提供的入口。
2. **分发物必须自包含。** 构建机上的 `/opt/homebrew`、`~/Library`、源码目录，在用户机器上都不存在。凡是被链接进来的东西，要么随包，要么在文档里让用户装。
3. **CI 必须执行真正发货的那条路径。** 只在打 tag 时触发的流水线，合并前一次都没跑过——等于没验。发货路径要在 PR 阶段就跑一遍。
4. **窗口程序必须落盘日志。** `console=False` 的 App 双击启动没有终端，`print` 出来的错误会凭空消失，只剩一个打不开的图标。
5. **一次只改一个变量。** 打包问题经常伪装成业务 bug（比如「首页 502」看起来像后端崩了，其实是 WebView 分支被误触发）。

## 陷阱目录

按发生阶段分组。判据列是**可以写进 CI 的断言**，不是感觉。

| # | 阶段 | 现象 | 根因 | 判据 |
|---|---|---|---|---|
| 1 | 打包 | 入口脚本找不到业务模块（`ModuleNotFoundError`） | 用 `runpy.run_path()` 按路径执行入口，PyInstaller 分析不到 import，依赖图为空 | 入口必须是静态 `import`；打包后启动一次 |
| 2 | 打包 | 配置文件被版本库忽略，打出来的包缺构建脚本 | `.gitignore` 里 `*.spec` 之类的通配符误伤 | `git ls-files` 确认打包配置已跟踪 |
| 3 | 打包 | 静态依赖下载源返回 410，构建随机失败 | 依赖第三方下载站的老接口 | 下载后必须 `--version` 实跑验证；多源兜底 |
| 4 | 启动 | 端口上没有任何监听，浏览器 502，源码跑也一样 | 传了 `window_size`/`fullscreen` 之类参数，框架判定为 native 模式，缺可选依赖直接 `exit(1)` | 启动后轮询入口 URL 必须 200 |
| 5 | 启动 | 进程数在几十秒内涨到上百，日志刷屏「地址已被占用」 | 冻结后 `multiprocessing` 的辅助进程用可执行文件自身重启程序，缺 `freeze_support()` 就变成无限自我复制 | 启动后进程数上限断言（正常 2 个） |
| 6 | 启动 | 双击无反应，无任何错误信息 | 窗口模式无终端，标准输出被丢弃 | 程序自己把 stdout/stderr 落盘到用户可写目录 |
| 7 | 分发 | 换台机器就报库找不到 | 二进制动态链接到构建机的包管理器路径 | `otool -L`（或 `ldd`）断言不含构建机路径 |
| 8 | 分发 | 安装包版本、包内版本、tag 三者不一致 | 打包配置里硬编码版本号 | 三处同源；CI 比对包内版本与发布版本 |
| 9 | 分发 | 打包机上挂载失败报「资源忙」，且报错被静默吞掉 | 上次运行被打断，镜像仍 attached；命令带 `-quiet` | 挂载前先清理同一镜像的残留设备；失败要给原因 |
| 10 | 脚本 | `set -u` 下报变量未定义，变量名后面跟着中文 | 多字节字符被吃进变量名 | 一律写 `"${VAR}"`，不要写 `"$VAR中文"` |
| 11 | 分发 | 同一个产品发多个变体（如「浏览器版 / 窗口版」），用户下到的那份和名字说的不是一回事 | 变体差异靠构建者记忆，产物里没有任何可读标记 | 产物内写渠道标记（如 `Resources/<VARIANT>`），验收时与文件名交叉比对 |
| 12 | 验收 | 按 pid 找监听端口，抓到的却是无关进程的端口，探活永远失败 | `lsof` 的选择条件默认是「或」，`-p` 与 `-i` 并列等于筛全机器 | 必须 `lsof -a -p <pid> -iTCP -sTCP:LISTEN` |
| 13 | 构建 | 连打几次包之后磁盘满，后续构建全失败 | `mktemp -d` 的中间产物从不清理，一次 1GB 级 | 构建脚本挂 `EXIT` 清理临时目录；构建前查余量 |
| 14 | 打包 | 「瘦包」体积莫名涨了几十 MB | 框架里 `try: import 可选后端` 一句，打包器就把整个可选依赖树拖进来 | 瘦包要断言可选依赖**不存在**（import 必须失败），而不是「大概没装」 |
| 15 | 验收 | 窗口类产物的验收结果时绿时红 | 验收依赖图形会话（Aqua/WindowServer），环境不满足时静默跳过 | 环境不满足要显式打 `SKIP`，且该门不得记为 `pass` |

### 逐条展开（最容易复发的七条）

**#4 native 模式被误触发。** 框架的签名里 `native=False` 是默认值，但 `window_size` 一旦非空就会把 native 改成真（NiceGUI 3.18 `ui_run.py:239`）。缺 `pywebview` 时它 `sys.exit(1)`，端口上什么都不监听——所以浏览器报 502，而源码直接跑也 502，很容易误判成「打包坏了」。修法是别传只对 native 有意义的参数，并显式 `host='127.0.0.1'`（本地工具没有理由暴露到局域网）。

**#5 缺 `freeze_support()`。** 冻结后子进程的命令行长这样：

```
VideoToText -B -S -I -c "from multiprocessing.resource_tracker import main;main(20)"
VideoToText --multiprocessing-fork fd=3 ...
```

bootloader 不认识这两种命令行，就当成「又一次正常启动」：子进程里再创建一个 tracker、再启动一个 App……40 秒涨到 86 个进程，全部去抢同一个端口。PyInstaller 的运行时钩子已经把 `freeze_support()` 换成了能识别这类命令行的版本，但**必须显式调用**，且必须是入口的第一条语句。

**#6 没有日志的窗口程序等于黑盒。** 在入口处 `os.dup2` 到 `~/Library/Application Support/<App>/app.log`，连 uvicorn 这种直接写文件描述符的输出也能抓到。这一条本身不修 bug，但没有它，#4 和 #5 都只能靠猜。

**#7 动态链接的陷阱。** 从本机 `PATH` 兜底拿到的二进制通常是动态链接的，构建机上跑得好，用户机器上直接废。分发前必须 `otool -L`（macOS）/ `ldd`（Linux）看一眼，并把它写成 CI 断言——这不是一次性检查，是每次构建都要过的门。

**#11 变体要落成产物属性。** 一个产品出两个包（浏览器版 / 原生窗口版）时，最容易出的错不是构建失败，而是**错位**：名字写着窗口版，装上去打开却是浏览器。人眼看不出来，日志里也不会报。做法是把变体写成产物里的一个可读文件（`Resources/<VARIANT>` 一行 `0/1`），入口读它决定行为，验收时再拿它和文件名对一遍——两个方向都断言，错位就藏不住。

**#14 可选依赖要显式排除，并反向断言。** 框架里常见 `try: import <可选后端>` 的写法（为了「装了就用」）。打包器的静态分析只看 import 语句，不看 try——于是瘦包里被拖进整棵可选依赖树（本项目里是 pyobjc 的上百个 `.so`）。排除之后还要加一条**反向**断言：瘦包自检时该依赖的 import 必须失败。只写「排除」不写断言，下次有人改 spec 就悄悄胖回去。

**#15 环境不满足时，SKIP 必须显式。** 窗口类产物的验收依赖图形会话；CI 机器、容器、无头服务器上不一定有。这时正确的行为是打一行 `SKIP` 并把该门记为 `unknown`，而不是让断言「因为没跑到所以没失败」——后者会在真正需要它的那天之前一直骗人。

## 十道门

与 `scripts/release_gate.py` 的 gate id 一一对应。每道门要么有 `observed` 证据，要么明确写 `unknown`/`blocked` 并给出原因。

| gate | 问的问题 | 典型证据 |
|---|---|---|
| `artifact_integrity` | 产物有名字、大小、校验和，且能被复算 | `shasum -a 256 -c` 输出 |
| `install_path` | 验的是**分发形态**，不是构建树里的目录 | 从挂载的 DMG 里启动的日志 |
| `cold_start` | 打包后的二进制真的启动了，入口可访问 | 首页 HTTP 200 + 关键内容命中 |
| `self_contained_runtime` | 不依赖构建机的路径 | `otool -L` 输出、随包二进制 `--version` |
| `code_signing` | 签名状态写清楚了，用户知道怎么打开 | 签名类型声明 + 首次打开说明 |
| `log_capture` | 出问题时有地方可查 | 日志文件路径与首屏内容 |
| `process_hygiene` | 没有失控的子进程 | 进程数断言输出 |
| `ci_exercises_shipping_path` | CI 跑的是发货路径，不是另一套 | 同一脚本在两个 workflow 里的调用记录 |
| `version_consistency` | 包内版本 == 发布版本 == 文件名 | 包内版本读取输出 |
| `first_run_instruction` | 用户拿到后知道第一步做什么 | 安装说明文件内容 |

`release_gate.py` 只核对**证据结构与引用**：哈希、版本一致性、`pass` 是否有观测证据、ad-hoc 签名是否配了首次打开说明。它不判断产物好坏，也不给发布许可。

## 教学与评审安排

给集团内要接手这条链路的人。三次共学，每次 60–90 分钟，都要求动手，不接受只听。

**第一次：看清「能跑」和「能装」的差别。**
准备一个能跑的本地项目，让它打包。预期会遇到 #1（依赖图）和 #6（没日志）。作业：把自己的 App 启动日志落盘，并贴出首页 URL 返回码。

**第二次：把验收写成断言。**
把「检查清单」改成一个脚本：挂载、查结构、查静态链接、启动、轮询入口、数进程。要求脚本在没有人为判断的情况下给出通过/失败。作业：给一个故意做坏的包（比如删掉随包依赖），让脚本失败并给出原因。

**第三次：让 CI 跑发货路径。**
把发版流水线拆成「PR 阶段真打一次 + 打 tag 时上传」，两次用同一个验收脚本。作业：跑一次完整发布，交一份 `release_gate.py` 能接受的清单。

**评审者用的三条硬问题**（不满足就别合并）：

1. 你验的是构建树里的目录，还是用户真正下载到的那个文件？
2. 这个断言在 CI 里会跑吗？在哪个 workflow、哪个触发条件下跑？
3. 用户第一次打开会遇到什么？这句话写在哪个文件里？

## 参考实现

`jaminliu89/video-to-text` 固定提交 `b8261f45d90cc5ec9353769ac78d575b4b264dc3`（tag `v0.5.2`）：

| 文件 | 作用 |
|---|---|
| `packaging/video2text.spec` | one-dir 打包，版本取自 `VERSION`，排除无关重型依赖 |
| `packaging/launcher.py` | 入口：日志落盘、可写目录、随包二进制注入、`freeze_support()` |
| `scripts/build_dmg.sh` | PyInstaller → 注入静态 ffmpeg → ad-hoc 签名 → `hdiutil` 封 DMG |
| `scripts/verify_dmg.sh` | 十道门的可执行版本（挂载/静态链接/启动/进程数） |
| `.github/workflows/ci.yml` | PR 阶段就打一次 DMG 并验收 |
| `.github/workflows/release.yml` | 打 tag 时构建并附到 Release |

Prism 不复制这些脚本。要在新项目里用，读该固定提交的实现，按本文件的判据重新验收；不要把这套脚本当成本仓库的运行时依赖。
