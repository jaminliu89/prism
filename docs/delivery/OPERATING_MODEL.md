# Prism 项目与交付简化规则

本规则的目标不是追求仓库数量最少，而是让提出目标的人只面对一个入口、一个负责人和一份交付结果。它适用于 Prism 统管的工程任务；不替代各独立产品的安全、发布和代码所有权。

## 1. 用户只面对一条主线

- **唯一用户入口：** Prism Mission（当前跨项目 Mission 为 [#38](https://github.com/jaminliu89/prism/issues/38)）。用户不需要分别维护 WP、仓库 Issue、PR 或 Agent。
- **唯一总负责人：** Prism 的当前执行 Agent 对目标恢复、范围、任务排序、跨仓库协调、集成和最终报告负责。不得把“某仓库有 owner”解释为把协调工作交回用户。
- **内部任务卡：** 各仓库 Issue/PR 仅作为代码变更、CI 和审查的证据载体。Prism 负责创建/更新/关联；除非用户明确要求，否则不要求用户逐卡指挥。
- **唯一交付报告：** Prism 汇总所有关联仓库的当前 SHA、CI、独立审查、真实产品验收、阻塞与下一动作。单个 PR 合并不等于整个 Mission 完成。

## 2. 执行默认单车道

- 一个 Mission 同一时间只推进一个可执行的写入切片；同一责任域只允许一个写入者。
- 不因两个任务没有依赖关系就默认并行。只有并行能显著缩短交付时间、改动目录完全隔离、接口已冻结且集成负责人明确时，Prism 才可在内部启用并行；并行不是默认，也不增加用户的协调工作。
- 任务顺序由 Prism 根据硬依赖、阻塞和最小可验证价值决定。完成一个切片后重新读取真实仓库状态，再选下一个。
- 连续两次验证失败进入 DEBUG；先复现和定位根因，不继续开新分支或堆修复。

## 3. 仓库策略：一个产品优先一个仓库，不是集团所有代码一个仓库

### 默认单仓库

新项目默认一个主仓库，容纳该产品的应用代码、测试、文档、部署配置和本产品内部模块。不要因为 Agent 角色、部门名称、功能模块或任务卡数量拆仓。

### 只有满足真实边界才拆仓

只有存在以下至少一项且拆分收益明确时，才新建独立仓库：

1. 需要独立版本号、发布节奏或兼容承诺；
2. 有不同安全/权限/密钥边界；
3. 运行时、语言栈或依赖生命周期明显不同，放在一起会造成实质负担；
4. 是可被多个产品独立复用的工具/SDK，且需要独立维护和发布；
5. 有明确的法律、许可证、数据隔离或外部协作边界。

拆仓前先记录：为什么不能留在主仓、跨仓接口、版本策略、维护责任、CI/发布责任和回滚方式。只因“让某个 Agent 负责”不构成拆仓理由。

### 现有仓库不做机械合并

Prism 是工程规划/集成入口；DCT 是可独立使用的确定性执行工具；VibeGuard 是独立安全审查产品。它们有不同产品职责和信任边界，暂时保留各自主仓。Prism 统一编排，不复制它们的实现，也不把它们的源码强行搬进 Prism。

## 4. 谁负责什么

| 角色 | 唯一责任 |
|---|---|
| Prism（总负责人） | 用户目标、范围、优先级、依赖、集成、跨仓状态、交付报告 |
| 当前实现者 | 当前单个切片的代码和本地验证；不自行批准自己的成果 |
| 独立审查者 | 对指定仓库、指定提交 SHA 做真实独立审查 |
| 产品仓库 | 保存该产品的代码、测试、CI 和发布事实 |
| 用户 | 只决定无法安全推断的产品取舍，以及费用、权限、不可逆和生产发布等高风险事项 |

“PM/Architect/Critic/QA”可以是工作视角，不代表存在独立人员。实现者不能换一个 Agent 名称后自我审批。

## 5. 统一状态与汇报

Prism 每轮只需要给用户报告：

1. 本轮推进了什么（仓库、PR、提交 SHA）；
2. 哪些检查真实通过，哪些未验证；
3. 当前唯一阻塞是什么；
4. Prism 接下来会推进什么；
5. 是否需要用户做一个不可替代的决定。

不得要求用户自己汇总不同仓库状态。缺少远端证据时明确写 NOT_VERIFIED/BLOCKED，不用 Issue 关闭、本地 JSON 或角色声明冒充通过。

## 6. 对本轮 ENG-DELIVERY-2026-11 的应用

- Prism #38 是唯一用户级 Mission；#39–#42、DCT #3/#4、VibeGuard #11、下载器 #74 保留为内部工作与各产品证据引用。
- 现有 PR #43、DCT PR #2、VibeGuard PR #9、下载器 PR #73 不做批量合并或仓库迁移。每个 PR 仍按自己的真实 SHA、CI、独立 Review 和服务端策略判断。
- 任务队列只给出一个下一执行项；完成并核验后再选下一个，不再默认并行 WP-01 与 WP-03。
- 这条规则先应用于本 Mission；验证有效后再作为新项目默认，不回头机械改造所有历史仓库。

## 7. 非目标

- 不把整个集团变成一个超大单体仓库。
- 不创建新的集团看板、Agent 调度平台或第二套 Foundry 生命周期。
- 不删除现有 Issue/PR，不重写历史，不自动迁移仓库。
- 不降低独立审查、CI、远端保护或产品验收要求。
